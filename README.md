# GSB Bugfix Task
## 题面
双卡聚合终端升级 MPTCP 后，地铁里看视频还是卡，抓日志发现主路径闲着、备份路径在硬扛。mptcp_subflow_scheduler.py 的 SubflowScheduler 负责子流选择和映射，现在备份子流在主路径正常时仍被派数据，流量跑错运营商；两条子流 RTT 差很大时还按轮询调度，接收端重组缓冲区直接堵死；DSS 映射里 data-level 长度和子流长度混用，映射整体错位；子流断开后没把未确认数据重注入，下载卡在同一个偏移；MP_CAPABLE 握手失败没回退普通 TCP，连接直接失败；收到 RM_ADDR 后还往旧地址发探测包；多子流共用全局序列号但锁粒度太大，吞吐只有单流水平；重复数据按子流序号去重，跨子流的重复完全没识别；新增子流时没重新协商 MPTCP 选项，对端当成普通 TCP；同时打开时两个方向都建流，令牌冲突；弱网切换时子流优先级更新滞后，画面黑几秒；进程重启后子流状态全丢，长连接一起重建。终端侧同时插着两张卡，运营商网络质量差很多，研发希望先把调度和重注入做稳，再谈聚合带宽，现在体验很差，退订的人已经上来了，客服那边已经接到不少投诉，很棘手。要求调度、映射和故障重注入形成一个可恢复的整体，切换时不能把已发数据弄丢。这十五个用例眼下全是失败，没有一条幸免。
