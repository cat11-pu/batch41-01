# GSB Bugfix Task
## 题面
数据中心两台核心交换机之间上了 MACsec，周五做密钥轮换时业务断了四十秒，抓包看是 SAK 换完旧密钥还在用。macsec_kay_guard.py 的 KayGuard 负责 MKA 和 SAK 分发，现在 CAK 名称不匹配也照样建 CA，任意参与者都能来当 key server；key server 优先级相同时不比 SCI，两个交换机同时下发 SAK；SAK 的密钥号回绕不处理，旧密钥被重新启用；MKA 生命周期过期不删 SA，旧 SA 一直能解密；接收 SA 的关联号和包号窗口不校验，重放包被当成正常流量；包号耗尽不触发重钥，链路直接停住；cipher suite 不一致时只取第一个，两端算法对不上；ICV 校验失败只加计数不丢包，坏包还是进业务；MACsec 和 MKA 的 SCI 端口号不一致，SA 被绑到错误的成员口；key server 切换时新旧 SAK 没有重叠窗口，切换必然丢包；EAPOL-MKA 报文长度异常不拒绝，解析时越界读；链路闪断后 MKA 不重新协商，SA 永久停在 Down。值班同学现在不敢再做轮换，怕再断一次。这条链路承载的是核心存储和虚拟化迁移流量，断一次就要重建半个集群，厂商文档里对密钥轮换的描述前后矛盾，大家不敢照做，现在只能把 MACsec 暂时关掉，链路裸奔，安全队已经发了整改单，现在压力很大，安全队天天催，不能再拖。要求 CAK、SAK 和接收窗口三层状态可恢复，轮换期间业务不能感知。十五条用例逐项核对，通过数仍然是零。
